# Гибридный маппер: нейросеть → параметры → универсальный алгоритм → карта

Этот документ описывает новую гибридную систему (`osu_mapper/hybrid/`, скрипты `*_hybrid*.py`).
Старый пайплайн (Model 1–4, `train.py`, `generate_beatmap.py`) не тронут и работает как раньше.

---

## 0. Почему старая схема упиралась в потолок

1. **Loss Model 3 — это сумма несравнимых чисел.** `train.py` складывает: CE аккордов (с весами классов до 8×),
   2× BCE линий, 1.5× BCE лонгнот (`pos_weight` до 20), 0.5× SR и `0.05 × SmoothL1` **в миллисекундах**
   (+ 5× log-вариант) для предсказания «прыжка» Δt до следующей ноты. Следующая нота может быть и через 1/4,
   и через 1/2 бита — у такой многомодальной цели регрессия имеет высокий неустранимый пол. Отсюда «11 и ниже никак».
   Режим `--self_improve` считает совсем другую величину (`CE без весов + 0.3·DPO`), поэтому его 0.4 с 11 сравнивать нельзя.
2. **Самокоррекция переписывала основные веса.** `train_model_3_self_improvement` сохраняет результат не только
   в `model_3_transformer_self_improved.pt`, но и **поверх `model_3_transformer_best.pt`**, причём учит их другой целью
   (без голов LN/Δt, без весов классов) и с другим конфигом (`d_model=128`). Поэтому после самокоррекции обычное
   обучение стартовало со «сдвинутых» весов, и loss прыгал до 14 — та самая бесконечная карусель.
3. **Авторегрессия «прыжками».** Каждая ошибка Δt сдвигает всё, что после неё; при обучении модель видит
   правильную историю (teacher forcing), а при генерации — свою собственную, с ошибками.
4. **Неустранимое:** маппинг — задача «один ко многим». Для одной песни существует много правильных карт, поэтому
   никакой loss относительно ОДНОЙ эталонной карты не уйдёт в ноль на валидации. В новой схеме эта неопределённость
   вынесена в явный «стиль» (вектор условий) и в распределения по параметрам.

## 1. Как устроена гибридная система

```
аудио ──► 8 аудио-представлений ("токенизаторов") ──► нейросеть (ОДИН проход, без авторегрессии)
                                                              │
                                     параметры для каждого 10-мс кадра
                                                              ▼
                     универсальный детерминированный алгоритм (O(N), один проход) ──► карта .osu
                                                              ▲
     эталонная карта ──► солвер (точная обратная функция) ────┘  (цели для обучения, 100% точно)
```

### 1.1 Универсальный алгоритм (`osu_mapper/hybrid/renderer.py`, `params.py`)

Карта описывается плотной дорожкой параметров — одна строка на каждые **10 мс**:

| Параметр | Значение |
|---|---|
| `time_class[f]` | 0 = в кадре нет события; `k>0` = событие ровно в `10·f + (k−1)` мс → **точность 1 мс** |
| `lane_code[f]` | как выбрать дорожки (25 классов, см. ниже) |
| `stagger[f, m]` | доп. сдвиг в мс для m-й ноты аккорда (если ноты аккорда стоят не в одну мс) |
| `ln_flag[f, m]` | m-я нота — лонгнота |
| `ln_len[f, m]` | длина лонгноты в мс (точно) |
| `overflow` | разреженный список «вырожденных» объектов, которые плотный язык выразить не может (отрицательное время, LN нулевой длины, две ноты в одной дорожке ближе 10 мс) — у ранкнутых карт он пуст |

**Коды дорожек** — 10 *относительных* операторов + 15 явных масок:
`SAME` (джек/чордджек), `ALT` (трель: как два события назад), `SHIFT_R/L` и `ROT_R/L` (роллы, с переходом 4→1),
`SHIFT_R2/L2` (сплиты), `MIRROR`, `COMPLEMENT` (джамптрели), `M0001…M1111` (явные аккорды).
Солвер всегда выбирает первый подходящий оператор, иначе явную маску — кодирование однозначное.

Ключевая идея: **память дорожек и занятость лонгнотами хранит алгоритм, а не сеть.** Сеть предсказывает
*отношения* («повтор того же звука» → джек, «чередование двух звуков» → трель, «восходящая мелодия» → ролл) и
поэтому может работать за один проход, без авторегрессии. Отдельная голова «размер аккорда» не даёт ошибке размера
аккорда распространяться по цепочке относительных кодов.

**Гарантия:** `render_track(solve_map(map)) == map` бит-в-бит для ЛЮБОЙ 4K-карты (линия, мс начала, мс конца,
тап/LN каждого объекта + все тайминг-поинты). Почему это всегда так: любое время выражается как кадр + смещение
+ stagger, любой аккорд — явной маской, любая длина LN — целым числом мс, а всё, что не влезло, попадает в `overflow`.
Солверу **не нужно ничего «подбирать»** — это не оптимизация и не криптография, а детерминированная обратная
функция за O(N): тысячи карт проверяются за секунды.

Иерархия параметров:
* **глобальные** — SR и вектор стиля (`nps, ln_ratio, chord_mean, jack_ratio, alt_ratio, roll_ratio, symmetric_ratio,
  explicit_ratio, offgrid_ratio, od`), солвер считает его из каждой карты; при генерации его можно задать руками;
* **покадровые** — таблица выше;
* **ручки алгоритма при генерации** — плотность (порог событий), максимум аккорда, запрет быстрых джеков,
  поведение лонгнот, привязка к сетке и т.д. (таблица в разделе 4). Именно они дают «любую сложность и плотность».

### 1.2 Нейросеть (`osu_mapper/hybrid/model.py`, `audio_features.py`)

**Аудио-представления («токенизаторы»)** — каждое описывает звук по-своему, все выровнены по 10-мс кадрам:

| Имя | Размер | Что ловит |
|---|---|---|
| `mel_fine` | 64 | лог-мел, окно 21 мс — атаки, транзиенты |
| `mel_mid` | 96 | лог-мел, окно 85 мс — тембр/инструмент |
| `pitch` | 96 | полутоновый спектр A0…A8, окно 341 мс — мелодия и бас |
| `chroma` | 12 | доли энергии по нотам — гармония |
| `onset` | 10 | спектральный поток по 8 полосам + superflux — где что-то началось |
| `hpss` | 34 | перкуссия против гармонической части (median-filter HPSS) — барабаны vs тянущиеся звуки |
| `fine_env` | 20 | огибающая энергии с шагом **1 мс** внутри кадра + производная — миллисекундный тайминг |
| `spectral` | 8 | громкость, центроид, ширина, rolloff, flatness, ZCR, баланс НЧ/ВЧ, поток |
| *опц.* `encodec24` | 128 | латенты нейрокодека EnCodec (то, что квантуется в «токены», как у MusicGen/Suno) |
| *опц.* `mert95m` | 768 | самообучаемые музыкальные эмбеддинги MERT |
| *опц.* `demucs_stems` | 128 | разделение на барабаны/бас/вокал/остальное (Demucs) + мел по каждому стему |

Опциональные нейро-токенизаторы включаются при подготовке датасета:
`--external` без имён — все три (`encodec24 mert95m demucs_stems`), либо перечислите нужные (`--external encodec24 mert95m`).
Пакеты ставятся вручную: `pip install encodec transformers demucs`. Веса скачиваются автоматически: перед обработкой
песен скрипт загружает каждую модель и прогоняет её на секунде тишины (в логе `[external] ...: loading model` → `OK`);
если пакета нет или загрузка не удалась, он сразу останавливается и пишет, что установить. Кэш весов: `~/.cache/torch`
(EnCodec, Demucs) и `~/.cache/huggingface` (MERT). Обученная с ними модель требует те же пакеты и при генерации.
Что именно принимает обученная модель, показывает `python inspect_hybrid_checkpoint.py`.
Кодировщики и STFT считаются на GPU, если он есть (`--device auto`, можно `--device cuda:1`); устройство печатается в логе (`[external] encoders run on: cuda`).
(В песочнице разработки реальные модели не запускались — там закрыт доступ к хостингу весов.)
**Качество звука:** `--quality_variants mp3_48k lowpass_6k` сохраняет признаки ещё и для пережатого/обрезанного
аудио; при обучении сеть случайно получает разные варианты. Все признаки нормируются по песне — громкость файла не важна.

**Сеть:** стемы представлений + «модальный дропаут» (сеть учится работать при отсутствии любого из них) →
дилатированные свёртки на 100 кадр/с (миллисекундные детали) → трансформер с RoPE на 25 кадр/с (контекст ±10 с) →
обратное повышение частоты + skip → головы для каждого параметра. Условия (FiLM в каждом блоке): SR, стиль (с
масками «неизвестно»), длинно-независимая сводка всей песни (attention-pooling по 1-секундным признакам).
**Абсолютного времени и «прогресса песни» сеть не видит вообще.** Пресеты: `tiny` 0.35M, `small` 2M, `base` 10M,
`large` 34M параметров.

### 1.3 Обучение (`train_hybrid.py`, `losses.py`)

* Цели для каждого кадра даёт солвер, поэтому loss плотный и точный до миллисекунды. Главный член — `time`:
  кросс-энтропия по 11 классам «нет события / событие на 0…9 мс кадра» с гауссовым размытием σ (3 мс → 1 мс):
  промах на 1 мс почти бесплатен, на 30 мс — как полный промах. Это и есть **помиллисекундный loss по таймингу нот**.
* Остальные члены: код дорожек, размер аккорда, stagger, тап/LN, длина LN (лог-корзины + остаток), авто-стиль.
  **Каждый член — нормированное среднее (~O(1))**, все печатаются отдельно; `total` сравним между запусками.
* Валидация каждую эпоху: полные песни из валидации прогоняются через сеть → алгоритм → **сравнение
  отрендеренной карты с эталоном** (`metrics.py`): F1 событий при допуске 0/1/2/5/10/16/32/64 мс, MAE тайминга,
  точность размера аккорда, F1 и ошибка длины LN, отношение плотности, `per_ms_loss` = среднее (1−F1) по всем допускам
  (0 = тайминг совпал бит-в-бит). `hybrid_best.pt` выбирается по F1 @16 мс на отрендеренных картах.
* **`--sr_balance`** (по умолчанию 0): карты редкой звёздности выбираются чаще. Вес карты умножается на
  (число карт в её диапазоне 1★)^−sr_balance: 0.5 — компромисс, 1 — каждый диапазон поровну. Нужно, если на высоких SR
  сеть не уплотняет карту, а только добавляет LN: карт 5–7★ в датасете мало, и без балансировки сеть их почти не видит.
  В начале обучения печатается распределение train-карт по звёздам.
* **`--rep_dropout mert95m=0.5`**: вероятность выключать отдельное представление при обучении (по умолчанию 0.15
  для всех). Высокое значение для MERT не даёт сети узнавать исполнителя по голосу и копировать стиль его карт
  (проверка без переобучения: `generate_hybrid.py --disable_reps mert95m`). Можно менять при `--resume`.
* Разбиение train/val — **по песням** (в старом коде перекрывающиеся чанки одной песни попадали и в train, и в val).
* **Несколько GPU:** запуск через `torchrun` включает DistributedDataParallel (NCCL на Linux, gloo на Windows, где
  NCCL нет). Каждая карта берёт свои случайные окна, градиенты усредняются; валидация и сохранение — на главном
  процессе. При N картах за то же число шагов сеть видит в N раз больше данных; если батч сильно вырос, можно
  поднять `--lr` (например, ×√N).
* **Один режим, одно пространство чекпоинтов** `checkpoints/hybrid/`, EMA-веса для оценки, `--resume` проверяет
  совместимость конфигов и продолжает ровно с того же шага (оптимизатор, расписание LR, EMA).
* Неразмеченные интро/аутро (дальше 2 с от первой/последней ноты) **не считаются «здесь нот нет»** — иначе сеть
  училась бы оставлять дыры.

### 1.4 Генерация (`generate_hybrid.py`, `inference.py`)

* Сеть применяется окнами ровно той длины, на которой училась (20.48 с), с перекрытием 50 % и Hann-смешиванием;
  алгоритм проходит весь трек одним проходом, перенося память дорожек и лонгноты через границы окон.
* **Плотность задаёт сама сеть** по запрошенному SR (SR — условие сети в каждом блоке). Никакой подгонки после
  генерации нет; SR результата по rosu-pp просто печатается. Насколько сеть попадает в SR, видно по метрике
  `SR error` (средняя ошибка SR отрендеренных валидационных карт) в логе обучения.

## 2. Предстартовые проверки (ваш пункт 3)

### 2.1 Проблема 1: существуют ли параметры, воспроизводящие КАЖДУЮ карту на 100 %?

**Да, по построению**, и это проверяется на всём датасете:

```powershell
python hybrid_solvability_audit.py --input_dir "F:\mania4k dataset" --out hybrid_audit_report.json
```

Скрипт для каждой 4K-сложности делает «карта → солвер → параметры → алгоритм → карта» и сравнивает бит-в-бит.
Выход с кодом 1, если хоть одна карта не совпала. Кроме того, он показывает, *насколько хорошо* язык параметров
ложится на реальные карты (это то, что придётся выучить сети): долю относительных кодов дорожек, энтропию кодов,
долю аккордов со stagger, долю нот вне сетки (они хранятся точно — язык не привязан к сетке; по аудиту старого
пайплайна ~6 % нот датасета отстоят от сетки 1/8–1/6 больше чем на 10 мс), число объектов в `overflow` и причины.
Те же проверки встроены в `prepare_hybrid_dataset.py` (карты с неточным round-trip исключаются из обучения).

Что входит в «100 %»: линия, мс начала, мс конца, тап/LN каждого объекта и все тайминг-поинты (8 полей).
Что не моделируется: хитсаунды/сэмплы объектов, сториборд — на геймплей они не влияют.
Важно отличать: *существование* точных параметров гарантировано; а вот *предсказать* их по аудио на 100 % нельзя
в принципе (см. п. 0.4) — поэтому качество сети меряется метриками отрендеренной карты, а стиль задаётся условиями.

### 2.1.1 Что это за параметры и как самому сгенерировать карту из них

Параметры конкретной сложности можно выгрузить в читаемый JSON и отдельно отрендерить карту **только из этого
файла** (алгоритм не видит оригинал):

```powershell
python hybrid_params.py list   "sample beatmaps\894666 Zekk - Vespera.osz"
python hybrid_params.py export "sample beatmaps\894666 Zekk - Vespera.osz" --diff Sirius -o sirius.params.json
python hybrid_params.py render sirius.params.json -o sirius_rendered.osu
python hybrid_params.py verify "sample beatmaps\894666 Zekk - Vespera.osz" --diff Sirius   # экспорт -> файл -> рендер -> сравнение
python hybrid_params.py verify "sample beatmaps"                                          # то же для всего датасета
```

Состав файла: тайминг-поинты (8 чисел на каждый) и список событий. Событие — группа нот, начинающихся в одном
10-мс кадре: `frame`, `offset_ms` (0…9), `lane_code` (25 вариантов), и для каждой ноты аккорда `stagger_ms` и `ln_ms`
(0 = тап, иначе длина лонгноты). Кадры без событий — это «нет ноты» (тоже параметр, но нулевой).

Пример (Zekk — Vespera [Sirius], 2203 объекта): 15 198 кадров, 1 517 событий; значимых параметров 8 152
(3 034 на события + 4 406 на ноты + 712 значений тайминг-поинтов); плотный тензор, который предсказывает сеть,
— 14 чисел на кадр = 212 772 значения (почти все — «нет события»). По всему датасету: 812/812 сложностей
воссоздаются из файлов параметров бит-в-бит, в среднем 3.8 значимых параметра на объект.

Важно понимать честно: это **точное перекодирование** карты, а не «магическое сжатие». Параметров примерно столько же,
сколько информации в самой карте (на каждую ноту — её время и дорожка, просто в удобной для сети форме: время с
точностью 1 мс относительно сетки 10 мс, дорожки — через отношения к предыдущим аккордам). Если вы введёте эти
параметры — получится ровно эта карта. Если параметры предсказывает сеть по аудио — получится карта настолько
близкая, насколько точна сеть (метрики `RENDERED MAPS vs reference` в логе обучения).

### 2.2 Проблема 2: очень длинные треки (час и больше)

Что сломалось бы в старой модели: признаки `progress`/`time_to_end` нормированы на длину песни (час растягивает
«интро» на 6 минут), энергия нормирована на среднее по треку, правило «48 тихих тиков после 60 % длины → стоп»,
абсолютные позиционные кодировки. В гибриде:

* сеть видит только окно 20 с (+ длинно-независимую сводку песни), абсолютного времени нет → 60-минутный трек
  обрабатывается ровно так же, как 3-минутный, окно за окном; память и время растут линейно;
* плотность задаётся локально (вероятность события в каждом кадре), а не бюджетом нот на песню;
* алгоритм рендерит весь трек одним проходом, без «последнего окна» и без обрезки;
* при обучении неразмеченные края песни не учат «здесь пусто».

Проверка:

```powershell
# одна песня подряд 12 раз: каждая копия должна получить (почти) ту же карту, без дрейфа плотности
python hybrid_long_track_test.py --audio song.mp3 --repeat 12 --sr 4
# разные песни подряд (час «диджей-сета»)
python hybrid_long_track_test.py --concat a.mp3 b.mp3 c.mp3 ... --sr 4
# синтетика на 60 минут (без файлов); --untrained проверяет только механику без чекпоинта
python hybrid_long_track_test.py --synthetic_minutes 60 --sr 4
```

Проверки (PASS/FAIL, отчёт в JSON): карта доходит до конца музыки; начинается вместе с музыкой; **нет дыр** —
промежутков без нот дольше `--hole_sec` (4 с), где ≥80 % времени звучит музыка; в режиме `--repeat` F1 событий
@2 мс между копиями ≥ 0.95 и коэффициент вариации числа нот по копиям ≤ 5 %; плюс время и пиковая память.
Юнит-тесты дополнительно проверяют, что предсказание не зависит от длины трека и позиции в нём, и что 60-минутный
вход полностью покрывается.

## 4. Ручки алгоритма при генерации

| Флаг | Что делает |
|---|---|
| `--sr` | целевой SR — условие сети, плотность и сложность паттернов сеть выбирает сама |
| `--threshold` | ручной порог события (по умолчанию — единый порог, выбранный на валидации и сохранённый в чекпоинте; от SR не зависит) |
| `--style k=v ...` | стиль: `nps ln_ratio chord_mean jack_ratio alt_ratio roll_ratio symmetric_ratio explicit_ratio offgrid_ratio od` |
| `--max_chord` | максимальный размер аккорда |
| `--jack_min_ms` | запрет повтора дорожки быстрее N мс (анти-минижеки) |
| `--hedge_ms`, `--hedge_sum` | (по умолчанию 60 / 1.5) два неуверенных события ближе 60 мс с суммой вероятностей < 1.5 — это одна нота, сеть колеблется где её поставить: оставляется более сильное. Уверенные 1/8 (0.9 + 0.85) не трогаются. `0` — выключить |
| `--jack_hedge_ms` | (по умолчанию 50) событие, повторяющее дорожку, нажатую меньше 50 мс назад, — дубль, выбрасывается (в реальных 4K картах таких повторов нет: 0 из 185 тыс. событий). `0` — выключить |
| `--merge_ms` | (по умолчанию 12) события ближе этого всегда сливаются в одно |
| `--style_from карта.osz` (+ `--style_diff имя`) | взять стиль готовой карты: плотность, долю LN, аккорды, роллы/альтернацию/джеки, off-grid. SR всё равно задаётся `--sr`, отдельные ключи `--style` перекрывают. Пример: `--style_from "Grimes - We Appreciate Power.osz"` |
| `--no_ln` | только тапы: `ln_ratio=0` в стиле + каждая LN превращается в тап |
| `--ergonomics 0.5` | алгоритмическая полировка дорожек: время нот, размер аккордов и LN остаются как у сети, перераспределяются только дорожки (поиск по лучу против быстрых джеков, длинных пассажей одной рукой, якорей, однообразных трелей). 0 — дорожки сети, 0.3–0.5 — чинит только плохие места (на настоящих картах меняет 1–4% дорожек), 1 — только эргономика (паттерны однообразнее). В консоль печатается «до → после». Готовую карту можно отполировать отдельно: `python polish_map.py карта.osz --strength 0.5` |
| `--hitsounds` (+ `--hitsound_volume 40,90`, `--hitsound_set auto/normal/soft/drum`, `--no_additions`) | автоматические хитсаунды по звуку: громкость каждой ноты следует громкости песни (тихий куплет тише, припев громче), набор звуков по секциям (~4 с: ударные → drum, тихие места → soft, иначе normal), добавки clap (удары малого на долях), whistle (яркие высокие акценты, редко), finish (крэш: громкая атака на сильной доле или начало секции, не чаще раза в 2 с). В аккорде добавка только на одной ноте. Ноты и дорожки не меняются. Для готовых карт: `python polish_map.py карта.osz --strength 0 --hitsounds` |
| `--disable_reps mert95m demucs_stems ...` | выключить отдельные представления звука без переобучения: сеть подставляет выученное «нет данных» (при обучении каждое представление выключалось в 15% случаев). Выключенные внешние энкодеры даже не загружаются. Полезно, если сеть «узнаёт» исполнителя по голосу (MERT) и копирует стиль его карт |
| `--threshold 0.5,0.4,0.3` | несколько порогов событий за один запуск (по сложности на каждый, признаки считаются один раз) |
| `--reference карта.osz` (+ `--reference_diff имя`) | эталонная карта той же песни: для каждой сгенерированной сложности печатаются F1 событий, точность/полнота, плотность, % пропущенных событий, F1 LN |
| `--ln_gap_ms`, `--ln_gap_beats` | (по умолчанию 40 мс и 1/4 бита) минимальная пауза между отпусканием LN и следующей нотой на той же дорожке; если сеть отпускает позже, LN укорачивается. В реальных картах пауза ≥ 40 мс в 99.9% и ≥ 1/4 бита в 96% случаев. Для плотных карт можно `--ln_gap_beats 0.125` (1/8). Если красных линий нет (оценённый BPM тоже даёт линии), действует только `--ln_gap_ms` |
| `--ln_threshold` | порог «тап или лонгнота» |
| `--snap_ms` | притянуть ноты и концы LN к сетке красных линий в пределах N мс |
| `--lane_temperature` | 0 = самый вероятный код дорожек, >0 = сэмплирование (разнообразие) |
| `--no_stagger` | все ноты аккорда строго в одну мс |

### Привязка к сетке и калибровка

* `--snap_ms` при обучении **не используется**: сеть учится на точных миллисекундах из карт. Привязка — только
  пост-обработка при генерации. Начала нот тянутся к ближайшему тику (из `--snap_divisors`), концы лонгнот —
  только к **предыдущему** тику (`--ln_snap_ms`), чтобы отпускание не становилось позже.
* Привязку стоит включать только при точном тайминге (шаблон или `--bpm/--offset`). С оценённым BPM сетка может
  быть сдвинута, и ноты «уедут» на чужие тики. При всех 8 делителях тики идут каждые ~7 мс, поэтому большой
  `--snap_ms` почти любую ноту куда-то притянет; для прямых 4/4 песен используйте `--snap_divisors 1,2,4`.
* Систематический сдвиг нот (часто — задержка MP3-декодера) и перекос длины лонгнот измеряются на валидации и
  сохраняются в чекпоинт (`onset_shift_ms`, `ln_length_scale`); генерация применяет их сама. Для уже обученного
  чекпоинта: `python calibrate_hybrid_checkpoint.py --checkpoint checkpoints/hybrid/hybrid_best.pt --data dataset_hybrid`
  (`--dry_run` — только показать замер). Вручную: `--onset_shift_ms`, `--ln_scale`.

## 4.5 Управление сложностью: чтобы сеть делала то, что запросили

Почему сеть «делает как может»: у большинства песен одна-две сложности, поэтому SR почти не несёт информации
сверх звука, и сеть учится его игнорировать. Что сделано (по этапам):

| этап | что | где |
|---|---|---|
| 1 | **усиление запроса** (classifier-free guidance): сеть прогоняется ещё и без SR/стиля, разница усиливается | `generate_hybrid.py --sr_guidance 2 --style_guidance 2` (можно списком `1,2,3`) |
| 1 | **порог событий по звёздам**: для каждого диапазона 1★ свой порог (подобран на валидации), при генерации берётся порог для запрошенного SR | пишется в чекпоинт при обучении и `train_hybrid.py --eval_only --update_checkpoint` |
| 2 | **производные карты**: каждая сложная карта прореживается до 4 уровней (слабые 1/8–1/16 и тихие места убираются первыми, аккорды урезаются), у каждой настоящий SR | `make_derived_maps.py --data dataset_hybrid` |
| 2 | **пары**: в батч кладётся то же окно той же песни на другой сложности | `train_hybrid.py --pair_prob 0.5` (батч чётный) |
| 3 | **потеря плотности**: ожидаемое число событий/нот в окне = как в эталоне | `--density_weight 0.3` |
| 3 | **потеря пар**: отношение плотностей двух сложностей = как у эталонов | `--pair_weight 0.3` |
| 4 | **метрика послушания**: генерация на SR−1/SR/SR+1, наклон (1.0 = каждая звезда запроса = звезда результата) | каждую эпоху в логе `SR response`, отдельно `hybrid_sr_response.py` |

Статистика карт по звёздам (сколько карт в каждом диапазоне 1★, доля LN, ноты в секунду):

```powershell
python beatmap_stats.py --input_dir "sample beatmaps"                 # папка с .osz (SR считается через rosu-pp)
python beatmap_stats.py --input_dir "новые карты" --list --min_sr 6   # + список карт от самой сложной
python beatmap_stats.py --data dataset_hybrid                         # готовый датасет: мгновенно, реальные / производные / валидация отдельно
```

Порядок работы:

```powershell
# 0) как слушается текущая модель (числа: slope / mono / sr@-1 sr@+0 sr@+1 / f1)
python hybrid_sr_response.py --checkpoint checkpoints/hybrid/hybrid_best.pt --data dataset_hybrid --guidance 1 2 3
# 1) пороги по звёздам в текущий чекпоинт (val_maps = все валидационные карты)
python train_hybrid.py --data dataset_hybrid --eval_only --update_checkpoint --val_maps 500
# 2) производные карты (аудио не пересчитывается; повторный запуск заменяет старые)
python make_derived_maps.py --data dataset_hybrid
# 3) обучение с новыми потерями (по умолчанию включены) + балансировка + MERT реже
python train_hybrid.py --data dataset_hybrid --preset base --epochs 30 --batch_size 16 --sr_balance 0.5 --rep_dropout mert95m=0.5 --response_weight 0.1
```

`--response_weight 0.1`: лучший чекпоинт выбирается по F1 + 0.1 × наклон отклика, то есть модель, которая
не слушается SR, перестаёт быть «лучшей». Производные карты в валидацию не попадают никогда.

## 5. Ограничения и что дальше

* Тайминг-поинты берутся из шаблона или оцениваются (одна красная линия); SV гибрид пока не генерирует (можно
  добавить каналы SV в дорожку параметров тем же способом).
* У MP3 бывает задержка декодера (несколько мс, постоянная для файла). Метрика `timing_bias_ms` в валидации
  показывает систематический сдвиг, если он есть.
* Сравнивайте качество по метрикам отрендеренных карт (`RENDERED MAPS vs reference` в логе), а не по `total`.
